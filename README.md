# Аналитика продаж — MVP

Веб-приложение для аналитиков и менеджеров: вход с двухфакторной аутентификацией, единый рабочий стол с конструктором дашбордов, список проектов и форма ввода данных с проверкой «на лету».

## Быстрый старт (Docker)

```bash
cp .env.example .env
docker compose up --build
```

Откройте http://localhost:8080. Swagger API: http://localhost:8080/api/docs.

Мониторинг (Prometheus + Grafana): `docker compose --profile monitoring up -d`, Grafana: http://localhost:3001.

### Трассировка запросов (опционально)

API поддерживает экспорт HTTP-трасс через OTLP/HTTP. По умолчанию экспорт выключен, поэтому для обычного запуска Collector не нужен. Чтобы включить экспорт, укажите в `.env`:

```dotenv
OTEL_TRACES_EXPORTER=otlp
OTEL_TRACES_SAMPLER=parentbased_traceidratio
OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318
OTEL_SERVICE_NAME=rt-analytics-api
OTEL_TRACES_SAMPLER_ARG=1.0
```

Имя `otel-collector` замените на адрес Collector, доступный из контейнера API. В Collector трассы принимаются по адресу `/v1/traces`. Доля семплирования задаётся значением от `0.0` до `1.0`; `1.0` сохраняет все корневые трассы. Для дочерних трасс решение о семплировании наследуется из входящего `traceparent`. Prometheus-метрики остаются отдельным каналом.

HTTP-трассы содержат метод, шаблон маршрута и код ответа. Query-параметры, заголовки, cookies, тела запросов и ответов, идентификаторы пользователей и тексты исключений не добавляются. Маршруты health-check, метрик и документации исключены. Трассировка охватывает HTTP-запросы API; Celery и SQL-запросы не инструментируются.

## Как требования заказчика реализованы

| Требование | Реализация |
|---|---|
| Вход по адресу, форма входа + второй фактор | `/login`: шаг 1 — email и пароль, шаг 2 — TOTP-код. Первый вход — привязка аутентификатора по QR. Сессия — httpOnly-cookie, ограничение числа попыток |
| Единый рабочий стол по размеру экрана | Сетка 12×12, высота строк считается от высоты окна — дашборд всегда помещается в экран |
| Настройки сбоку в зависимости от роли | Левая панель: свои и общие дашборды, проекты; пункт «Новый проект» — только у тех, кто может редактировать |
| 3 показателя на сегодня и сравнение с прошлым годом | KPI: объём воронки, активные проекты, выиграно с начала года — с % изменения к той же дате прошлого года |
| Графики по сегментам и услугам | Виджеты «Разбивка» по сегментам, услугам, менеджерам, стадиям |
| Как менялась «корзинка» за 4–6 недель + прогноз | Виджет «Динамика»: история за 4–12 недель + прогноз на 7–30 дней (модель Холта с затуханием тренда) с доверительным интервалом |
| Выбор: дашборд или список проектов | Панель слева; список проектов с поиском, фильтрами, сортировкой, выгрузкой в Excel |
| Карточка проекта: сведения по ТЗ | Форма проекта: описание, клиент и сегмент, услуга и её группа, тип платежа, этап по ТЗ, индикатор, прогноз и оценка, реализация через ДЗО, контроль руководства, отраслевые данные, год реализации, статус, сделанное и планы; финансы и маржа остаются без пересчёта |
| Аналитик сам собирает отчёт, может заменить диаграмму на кольцевую | Конструктор: добавить/удалить виджет, перетащить, изменить размер, сменить вид диаграммы (столбцы, кольцевая, круговая, таблица) в меню «⋯» |
| Ошибки при вводе — сразу, а не в конце | Проверка каждого поля при уходе с него, повторно — при каждом изменении; проверка дублей «клиент + название» во время ввода |
| Ввод данных на одном листе | Форма в две колонки на одном экране |
| Выпадающие списки | Услуги и группы услуг, тип платежа, индикатор, этапы по ТЗ, статусы оценки, ответственный, сегмент |
| Минимум ручной работы менеджера | Автоподсказка клиента по названию или ИНН, создание клиента прямо из формы, вероятность по выбранному этапу ТЗ, автоматический расчёт маржи, черновик сохраняется сам |

Этапы заказчика хранятся отдельным полем и не подменяют прежние стадии MVP: автоматическое сопоставление старых значений не выполняется. Суммы и их единицы не конвертируются. Статус оценки доступен только для проекта, принятого к прогнозу; отраслевые поля — только для отраслевого решения.

## Архитектура

```
Браузер ──► Nginx ─┬─► Next.js (React, TypeScript)       /
                   └─► FastAPI (Python 3.12, Pydantic)   /api
                          ├─ PostgreSQL (SQLAlchemy 2.0, Alembic)
                          ├─ Redis — кэш аналитики, лимит попыток входа
                          └─ RabbitMQ ─► Celery worker + beat — прогрев кэша
Prometheus ◄── /metrics ── FastAPI;  Grafana ◄── Prometheus
```

- **Аналитика** считается на Pandas: состояние воронки на любую дату восстанавливается из дат начала и закрытия проектов, без отдельных снимков.
- **Кэш**: результаты аналитики лежат в Redis 5 минут; любое изменение проекта сразу сбрасывает кэш. Без Redis приложение работает, просто без кэша.
- **Права**: пользователь видит и меняет только свои проекты; аналитик видит и редактирует все проекты; администратор имеет полный доступ.
- **Журнал действий**: входы, создание и изменение проектов, клиентов и дашбордов пишутся в таблицу `audit_log`. В карточке проекта показаны последние 10 событий: автор, дата, изменённые поля и значения до/после, включая финансовые строки. История доступна только вместе с самим проектом. Для старых неполных записей отсутствие значения обозначается явно; новые события сохраняют названия справочников на момент изменения.

## Локальная разработка без Docker

```bash
cd backend
python -m venv .venv && .venv/Scripts/pip install -r requirements-dev.txt   # Linux/macOS: .venv/bin/pip
# нужен PostgreSQL; для быстрой пробы можно SQLite:
export DATABASE_URL=sqlite:///dev.db REDIS_URL=
alembic upgrade head && python -m app.seed
uvicorn app.main:app --reload --port 8000
```

```bash
cd frontend
npm install
npm run dev     # http://localhost:3000, /api проксируется на 127.0.0.1:8000
```

На SQLite поиск без учёта регистра не работает для кириллицы. В PostgreSQL всё работает.

## Тесты и проверки

```bash
cd backend && pytest -q && ruff check app tests
cd frontend && npm run typecheck && npm run lint && npm run build
```

CI (`.github/workflows/ci.yml`) прогоняет тесты, применяет миграции на PostgreSQL и собирает Docker-образы.

## Что уточнить у заказчика

1. Точные формулы KPI: считать воронку по полной сумме или взвешенно по вероятности? С чем сравнивать — та же дата прошлого года (сейчас так) или весь прошлый год?
2. Что именно называется «корзинкой» — сейчас это объём открытой воронки.
3. Способ второго фактора: TOTP (сейчас), SMS или email; нужен ли вход через корпоративный AD/Keycloak.
4. Откуда брать данные: только ручной ввод или интеграция с CRM / 1С.
5. Целевое разрешение экрана, требования к хранению данных (152-ФЗ, реестр отечественного ПО).
